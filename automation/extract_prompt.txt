공지사항 본문에서 달력에 넣을 일정을 뽑아내는 작업이다.

work/pending/ 폴더의 .txt 파일을 전부 읽어라. 파일이 없으면 아무것도 하지 말고 끝내라.

각 파일마다 정확히 JSON 파일 하나를 만든다. 저장 위치는 그 파일 머리말의
'저장할파일:' 줄에 적혀 있다. 그 경로를 그대로 쓴다.

## 만들 JSON 형식

{
  "post_id": "<머리말의 글번호 그대로>",
  "board": "<머리말의 게시판 그대로>",
  "tab": "<머리말의 탭 그대로>",
  "title": "<머리말의 제목 그대로>",
  "url": "<머리말의 주소 그대로>",
  "posted_date": "<머리말의 게시일 그대로>",
  "extracted_at": "<지금 시각, 예: 2026-07-26T09:05:00+09:00>",
  "revision": 0,
  "needs_manual": false,
  "no_events_reason": null,
  "events": [
    {
      "slug": "apply-close",
      "summary": "장학금 신청 마감",
      "start_date": "2026-08-07",
      "start_time": "17:00",
      "all_day": false,
      "confidence": "high",
      "evidence": "신청기간 : 2026.7.27.(월) ~ 8.7.(금) 17:00 까지",
      "uid": null
    }
  ]
}

## 반드시 지킬 것

1. uid 는 언제나 null 로 둔다. 프로그램이 나중에 채운다. 절대 직접 만들지 마라.

2. 기간은 하나의 긴 일정으로 만들지 말고 "시작"과 "마감" 두 건으로 쪼갠다.
   "7/27 ~ 8/7 신청" -> "신청 시작"(7/27) + "신청 마감"(8/7) 두 개.
   이유: 여러 날에 걸친 일정에 'D-3 알림'을 걸면 시작일 기준으로 울려서,
   정작 중요한 마감 3일 전에는 아무 알림이 없다. 마감 관리가 이 달력의 목적이다.

3. start_date 는 반드시 YYYY-MM-DD 다. 다른 형식은 전부 버려진다.

4. 본문에 연도가 없으면(예: "8. 7.(금)") 게시일을 보고 판단한다.
   보통은 게시일과 같은 해다. 다만 그렇게 넣은 날짜가 게시일보다 두 달 이상
   과거가 되면, 그건 내년 일정이므로 연도를 +1 한다.
   요일이 함께 적혀 있으면 요일이 맞는지 확인해서 검산하라.

5. 시각이 본문에 없으면 start_time 을 null 로 두고 all_day 를 true 로 한다.
   시각이 있으면 "HH:MM" (24시간제) 으로 적고 all_day 를 false 로 한다.
   "17시까지" -> "17:00", "오후 2시" -> "14:00".

6. evidence 에는 그 날짜의 근거가 된 본문 문장을 그대로 옮긴다. 요약하지 마라.
   나중에 사람이 "이 일정이 왜 여기 있지?" 하고 확인할 때 쓴다.

7. summary 는 달력에서 한눈에 알아볼 수 있게 쓴다. 25자 안쪽이 좋다.
   "마감", "시작", "시험", "발표" 같은 말을 넣어 성격이 드러나게 한다.
   나쁜 예: "안내"  좋은 예: "2학기 장학금 신청 마감"

8. 일정이 하나도 없어도 JSON 파일을 반드시 만든다. events 를 [] 로 두고
   no_events_reason 에 이유를 한국어로 적는다.
   파일을 안 만들면 프로그램이 같은 글을 매번 다시 읽으려 든다.

## 일정으로 넣을 것과 넣지 말 것

넣는다: 신청·접수·제출 마감, 시험일, 발표일, 설명회·행사 일시,
        수강신청 기간, 등록금 납부 기한, 면접일

넣지 않는다:
  - 이미 끝난 일을 보고하는 글의 과거 날짜 (예: "지난 7월 20일부터 접수된
    이의신청은 48건이었습니다" -> 일정 아님)
  - "연중 상시", "추후 공지" 처럼 날짜가 특정되지 않은 것
  - 문서 번호나 법령 시행일처럼 내가 지켜야 할 일이 아닌 날짜
  - 게시일 자체

판단이 애매하면 confidence 를 "low" 로 적되 일정은 넣어 둔다.
빠뜨려서 마감을 놓치는 것이 잘못된 일정 하나보다 나쁘다.

## 하지 말 것

- 본문에 없는 날짜를 지어내지 마라. 추측한 날짜는 마감을 놓치게 만든다.
- 첨부파일(.hwp 등)의 내용을 아는 척하지 마라. 읽을 수 없다.
  본문만으로 판단할 수 없으면 events 를 [] 로 두고 needs_manual 을 true 로,
  no_events_reason 에 "내용이 첨부파일에 있음" 이라고 적는다.
- work/pending/ 과 state/extracted/ 밖의 파일은 건드리지 마라.
- 텔레그램으로 아무것도 보내지 마라. 발송은 다른 프로그램이 한다.
